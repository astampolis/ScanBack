# ScanBack operations and recovery

Assign named owners for administration, privacy requests, security incidents, certificates, mail, SQL backups and restores. Keep an offline record of the deployment layout and recovery access. Use synthetic data for monitoring and tests; do not put medical fields, contact addresses, coordinates, raw capabilities or authentication secrets into tickets, log messages or screenshots.

## Routine checks

- Monitor HTTPS `/health` for database readiness and `/health/live` for process liveness. Restrict monitoring details; health responses contain no connection strings. A healthy website alone does not prove that the separate worker is processing mail.
- Monitor `ScanBack.Worker` service status and Windows Application log source `ScanBack.Worker`, outbox oldest-pending age, retry/failed counts and provider acceptance. Configure alerts and bounded access/retention for operational metadata. Repeated service restarts, SMTP failures or growing outbox age need investigation.
- Check provider bounce/abuse notices and sender-domain alignment. An accepted SMTP transaction may still be filtered/bounced. Retries can duplicate a message after an uncertain transport outcome; no automated status means a human was informed or emergency help was dispatched.
- Check SQL backup completion, restore tests, disk capacity, patch levels, certificate expiry, worker retention runs and application availability after every maintenance restart.
- Keep IIS stdout and Failed Request Tracing off. Inspect W3C `#Fields` after configuration changes and ensure complete URI/query/referrer capture remains disabled on both IIS sites and upstream proxies/APM. Application logs must also omit raw identifiers and payloads. Restrict/rotate IIS, Windows, HTTPERR, proxy and provider logs according to their documented retention.

Production Web/Worker use DML-only database identities. Production startup does not apply migrations, create roles, create administrators or backfill data. Use the separate CLI under the migration operator identity during maintenance.

## Updating a release

Review the release and migration SQL first. Test the new package, migrations and recovery on an isolated, access-controlled copy, with mail redirected to a test relay and synthetic or properly anonymized data. A restored production database contains personal/health data and must receive the same safeguards; do not send its stored outbox to real contacts.

The updater expects a complete installation created by the supplied IIS installer. For a legacy web-only host, stop it, preserve its database/key ring/photos/config and IIS configuration, and perform a first installation into an empty code directory with the preserved external data. Resolve the old hostname binding during the maintenance window, without deleting its recovery backup. Run migrations/Identity-secret backfill under the operator identity and verify acceptance before retiring the old installation.

1. Obtain the trusted Windows package and verify its independent checksum. Stage/extract outside the installation/data trees. Keep its `deploy` scripts; run the new package's scripts, passing the actual custom paths/pool/site names where used.
2. Stop Web and Worker across **all** nodes. Put `app_offline.htm` into each Web root before stopping its application pool, stop both IIS sites, stop `ScanBack.Worker`, and disable automatic starts during maintenance. The update script performs these steps for a single server and waits for shutdown.
3. Take and verify a **coordinated recovery point** containing SQL, photos, key ring, Data Protection certificates/private keys, and protected configuration. Record SQL backup/log positions and code version. Pre-migration code backups alone cannot restore user data or reverse schema/data changes. Plan enough downtime for a consistent backup; confirm no other node writes while capturing it.
4. If upgrading a legacy layout with `Web\App_Data`, preserve/move its existing key ring and photos into the external DataRoot while hosts are stopped, and point the shared JSON at those directories. Keep the original encrypted key material and certificate/private key; do not generate a replacement ring. Verify/retain a protected copy, then archive/remove only that old `App_Data` directory. The updater refuses legacy runtime data under Web so it cannot delete it as part of code replacement. Run the new package's updater, which stops the single server, backs up the installed **Web/Worker/Tools** folders, replaces them, and leaves everything stopped:

   ```powershell
   .\deploy\Update-ScanBack.ps1 -PackagePath $PWD.Path
   ```

   It never deletes external config, photos or keys. It restores the prior code if copying fails, while remaining in maintenance. It never applies or reverses database changes. Its code backup directory is printed; protect/prune old code separately from personal-data backups. If you already stopped the service/site, the stop commands are harmless.
5. As the separate operator, run the installed **new** `Tools\ScanBack.Deployment.exe check-config --config ...`, then `migrate --config ...` and `initialize --config ...`, checking each exit code. Run `backfill-identity-secrets --config ...` for a legacy database before starting the new code. No old binaries may write Identity token rows during that transition. Do not store deployment credentials in shared configuration or IIS/service environment.
6. Clear temporary administrator/deployment environment variables. Run `deploy\Start-ScanBack.ps1 -HostName YOUR-HOST` with the correct config/install/pool/site parameters if customized. Verify HTTPS, existing-user MFA, sticker revocation, new synthetic mail through the worker and privacy/account controls. Confirm outbox processing resumes. Schedule the next restore test.

For a deliberately staged schema rollout, keep old/new compatibility explicit and reviewed. Do not run old code against a changed schema merely because files can be restored. Multi-node deployments require a shared key ring/storage design, coordinated worker ownership and deployment procedure beyond this single-server installer; do not scale by copying virtual-account configuration to another server.

## Rollback and failed startup

Keep both sites and the worker stopped. Preserve sanitized failure evidence. If the release made **no schema/data changes**, restore the backed-up Web/Worker/Tools folders while offline, reapply read/execute ACLs to the installation, confirm configuration compatibility, then start and run acceptance checks. `Update-ScanBack.ps1` automatically restores only code when its file-copy step fails; it intentionally leaves service/sites stopped for review.

If schema/data changed, use the reviewed forward fix or the coordinated database/photos/key/certificate restore procedure. Do not blindly run EF `database update` backward or restore only the database: that can lose new data or disconnect records from photos/keys. Account for user writes and externally sent mail since the recovery point; sent messages cannot be recalled. Document the chosen recovery point and expected data loss, and get the incident owner's authorization before replacing live user data. A failed IIS startup is not grounds to generate a new key ring.

For startup failures, check Windows Application events (ASP.NET Core Module/worker), installed .NET 10 runtimes, pool bitness/No Managed Code, `SCANBACK_CONFIG_FILE`, external file ACLs, machine certificate private-key ACLs and validity, SQL DNS/trust/schema and runtime DML grants. HTTP 500.19 often indicates missing/locked IIS configuration modules; 500.30/500.31 indicate application/runtime startup problems. Review [Microsoft's IIS troubleshooting guidance](https://learn.microsoft.com/aspnet/core/test/troubleshoot-azure-iis). Diagnose in an isolated test environment or use bounded administrative diagnostics with no request URLs/secrets; do not leave stdout logs or detailed errors enabled on the public site.

## Backups, restores and deletion

Back up the database, photos and full Data Protection key ring as one recoverable system. Retain every Data Protection certificate/private key needed to decrypt retained key files, including old certificates after rotation, plus any SQL encryption/backup keys. Protect SMTP/configuration backups because they contain credentials. Encrypt backups in transit/at rest, restrict access to named operators, store a separate offline/immutable copy, and keep encryption passwords/keys separately. Test a restore into an isolated machine at a documented interval. Record the measured RPO/RTO rather than promising untested recovery times.

Choose a documented backup expiry appropriate to your lawful purpose, obligations and recovery needs; the application cannot delete a record inside an immutable SQL backup. Do not claim live account deletion immediately erases historical backups. Make recovery copies inaccessible for ordinary use, expire them on schedule, and record deletion/withdrawal requests so a restore can reapply them before reopening service. Include recreated consent, revoked identifiers/invitations, deleted photos and account state in restore verification. Do not replay a restored outbox to real recipients without reviewing the recovery boundary.

Configure live incident retention through administration within supported limits and document the actual values exposed by the policy. The worker handles bounded incident/outbox/access/audit cleanup; check its progress, including after downtime. Public invitation/access expiry and identifier revocation are enforced on access even before cleanup. Health-data consent withdrawal and account deletion have separate immediate application behavior. Decide backup, access-log and SMTP-provider retention separately, and include them in the operator's notices/records. Preserve evidence subject to a lawful hold only under an authorized, documented procedure.

## Certificate and credential rotation

Public HTTPS renewal is separate from Data Protection. Install/validate the replacement HTTPS certificate with the correct DNS chain in LocalMachine/My, update only the IIS HTTPS binding to the new thumbprint, and test trusted HTTPS externally and from the monitor. Automate expiry alerts. Do not remove a Data Protection certificate when renewing the website certificate.

For Data Protection rotation, take a coordinated backup, provision a new machine RSA certificate, grant both runtime accounts and the operator private-key read access, and test decryption against a restored key ring before changing the active configuration. Put the previous certificate thumbprints into the external configuration's `Encryption:DecryptionCertificateThumbprints` array, retaining those certificates in `LocalMachine/My` **with their private keys and read ACLs**. The shared hosts use them explicitly to decrypt older key-ring files; keeping only the new active certificate is insufficient. A prior PFX-based certificate must be imported securely into the machine store and listed there before switching to a new active certificate. Retained decryption certificates can be expired; the active encryption certificate must be current. Include every required old certificate/private key in recovery backups.

Changing the active certificate protects newly created key material; it does **not** re-encrypt all old key-ring files. The key ring includes purpose-specific encryption used for health fields, identifiers, incident access/outbox and Identity authenticator/recovery secrets; deleting old keys or certificates can make them unreadable. This version does not offer a one-command bulk rewrap/old-certificate removal. Keep old keys/certificates until a separately reviewed migration and the retention/restore obligations allow removal. Restart Web and Worker together after configuration changes and verify existing accounts/data, not only a new synthetic user.

Rotate SMTP/runtime SQL secrets using protected configuration or your supported secret manager; never put replacements into shell history. Restart both hosts to ensure they read the intended version. Revoke superseded credentials at the provider after verification. Investigate suspicious credential exposure under the incident procedure; rotation does not invalidate already-copied public sticker/invitation URLs. Revoke/replace the affected capabilities explicitly.

## Privacy requests and incidents

Use the in-app export, consent withdrawal, contact unsubscribe and password-confirmed account deletion controls where appropriate. Authenticate requesters proportionately without collecting unnecessary health data. Administrators have limited account/incident metadata and do not receive a medical-profile browsing interface. Record requests and decisions in a restricted operator system with a stated retention period.

If a token, account or server may be compromised, contain access, preserve minimal restricted evidence, revoke affected identifiers/invitations/sessions as appropriate, rotate exposed credentials, and assess scope with the incident/privacy owners. Evaluate applicable notification duties and deadlines, including GDPR Articles 33/34, using the actual facts and qualified advice. A public URL remains transferable even with a well-configured server. Maintain current processor contacts and a tested breach-response procedure.
